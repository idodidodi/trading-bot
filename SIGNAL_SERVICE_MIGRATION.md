# Manual signal-service / trading-executor cutover

Prepared 2026-11-06. Repository publication and independent installer builds are authorized. No production cutover, broker requests or test alerts are part of this work. Production cutover requires explicit approval. Legacy executable publishing remains disabled.

## Ownership and dependency map

| Concern | Signal service | Trading project |
|---|---|---|
| Detection, OHLC caches, signal replay/price-path quality | Existing scanner/strategy modules, `backtest.py`, `backtest_jobs.py`, `csv_backtests.py`, detection-only `chasing_research.py` / `annual_near_backtest.py` | Consumes API or recorded files; no imports of scanner internals |
| Signal delivery | `signal_contract.py`, `signal_service.py`, private Postgres stream/subscriptions | `signal_client.py`, SQLite inbox/cursor |
| Telegram | All original routing, retries, callbacks, dismissal, personal/group preferences and chase state | Durable execution-fact outbox only; no Telegram credentials or client |
| User-reported position alerts | `position_monitor.py` remains alert-only, used by `divergence_chasing.py` | Independent copy for consumer research; never shares position tables |
| Automatic trading | No executor modules, worker, paper dashboard controls, or broker-account views | Alpaca paper, Bybit demo, provider-neutral gateway/Velotrade adapter, entry/exit/reconciliation policy |
| Journals | Legacy records archived privately after verification | Paper trades/status, demo policy/trades, simulation histories/reviews/reports, notifications, migration receipts |
| Backtests | Detection and quality observations | `momentum_policy.py`, `chase_simulation.py`, tracking/review/return-comparison tools |

The alert-only position monitor is deliberately retained because removing it would change existing Telegram behavior. It never owns broker orders or an account. Trading rules do not import it from the service. Read `TELEGRAM_ALERT_LOGIC.md` for alert semantics.

The independent project is [idodidodi/trading-executor](https://github.com/idodidodi/trading-executor), a separate private repository with its own desktop window, installer workflow, `pyproject.toml`, requirements, environment and journal. The signal repository no longer contains its source tree. No shared internal-table reads or signal-service Python imports are used by the executor. The current packaged runner supports Alpaca paper and Bybit demo only; the moved Velotrade gateway remains an independently tested adapter, not a newly activated production integration.

## Stopped-owner export and reconciliation

1. Record actual old worker/update/autostart owners on every machine. Disable old paper and demo entry policy, then stop the old process, updater and restart mechanisms. Disabling entries alone does not stop existing-position management. Stop the old execution owner before snapshot or enabling a new owner. Preserve its binaries/source, environment and a database backup.
2. Keep broker positions protected while stopped. Use read-only broker reconciliation to inventory account, symbol, side, size, average price, every entry/exit/protective order, client ID, provider order ID, fill, cancellation, and unknown intent. No new test orders or alerts. Decide each unresolved submission manually using its original identity; never generate replacement IDs or retry an ambiguous submission blindly.
3. With an explicit administrator export connection, run `scripts/export-execution.py --writers-stopped --output /absolute/protected/snapshot.json` and `EXECUTION_EXPORT_DATABASE_URL` set privately. This is a read-only repeatable-read export; the flag attests that operators stopped writers, it does not stop services. The file is exclusively created with mode 0600. Preserve its checksum.
4. On the isolated executor, run `python migrate.py --database /absolute/execution.sqlite3 --snapshot /absolute/protected/snapshot.json`. Import requires an empty journal, is atomic and idempotent for the same snapshot, preserves broker IDs/source IDs/embedded signal evidence, records counts/digest, and forces execution disabled. No broker calls occur. Run the same command with `--verify-only` before activation to compare every source table count and original ID/payload to the imported journal; config enablement is intentionally reset. Existing positions retain legacy references, while new trades record contract signal/event IDs.
5. Revoke/rotate the old broker-capable credentials and remove them from the signal installation. If Alpaca market data still needs credentials, supply a separate credential with no trading authority where the provider supports it; never reuse the executor environment. A file lock prevents concurrent owners of one executor journal, but cannot fence a copied journal or another host: credential rotation and stopping the old owner are mandatory operational fences.
6. After export/import verification, apply the new dashboard function and, with explicit approval, `cloud/execution-cutover.sql`. It moves old execution tables into private `execution_legacy`, preserves historical mixed momentum data there, and removes execution fields from replay reports. It never deletes broker history or touches Telegram queues/recipients/baselines. This one-time migration intentionally refuses reapplication rather than replacing an archive. Keep legacy data for audit/recovery, not as a second active journal.

Existing owned positions are reconciled rather than re-entered. Restored subscriptions preserve cursors; do not create a fresh live subscription to conceal a recovery gap. 6. Verify deployed source/manifest/health against the approved SHA at the actual destinations. Exercise API auth/empty consumption and dashboard reads safely; inspect existing Telegram state without sending a test alert. Verify no executor code/credentials in the signal runtime, one trading owner, independent storage and unchanged production Telegram routes. Record links, SHA, outcomes and any inaccessible destination as unverified.

## Recovery and limits

Pause entries before changing state; stopping the executor also pauses automated management, so reconcile broker protection first. Never start the old execution owner alongside the new one. After any new orders, use forward repair or reconcile and migrate the current journal back under a separately reviewed procedure; a source rollback cannot undo broker effects. Restore Telegram only from its own preserved journal and offsets.

The new execution-notice handoff adds an HTTP dependency. Notices are durably retried with the original ID/time and enter the unchanged Telegram queue; an API outage can delay them. No claim of identical wall-clock latency or exactly-once Telegram delivery is made. Legacy broker-adapter limitations remain; no live adapter certification was performed. SQLite is a single-owner execution journal, not a multi-host HA database. Historical simulation requires recorded candles; the executor does not gain access to signal-service candle tables.
